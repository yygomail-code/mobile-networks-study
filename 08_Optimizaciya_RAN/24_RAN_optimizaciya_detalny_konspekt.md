## 24.1 Рамка задачи: что именно оптимизирует Core

**Оптимизация RAN со стороны Core** — целенаправленное изменение параметров, политик и процедур
ядра (и связанных с ним узлов/интерфейсов), которое улучшает KPI и QoE радио-сети, не меняя
(или минимально меняя) настройки самого радио.

Зона ответственности:

| Может Core | Не может Core (но влияет косвенно) |
|---|---|
| QoS-профили: QCI/5QI, ARP, GBR/MBR, AMBR | Мощность, наклон/азимут антенн, MIMO-конфиг |
| Политики PCC (PCRF/PCF), правила и фильтры | Параметры планировщика, MCS, BLER-цели |
| Сессии и bearer'ы: setup/modify/release | Реакции RRC, таймеры радио |
| Мобильность: TA/зоны, RFSP, пулы, handover-процедуры | Пороги A3/A5/B1/B2 (настраиваются в RAN) |
| Paging: TA list, DRX/eDRX, повторы | Радио-параметры paging |
| Перегрузка: overload, backoff, admission-политика | Ёмкость радио (PRB), число сот |
| Транспорт: GTP-U, DSCP, MTU, размещение UPF | Транспортная ёмкость между eNB и Core (зона транспорта) |
| Данные: счётчики, трейсы, MDT, RCAF, SON-политики | Внутренние SON-алгоритмы вендора RAN |

**Ключевой принцип защиты:** Core отвечает за **доступность (accessibility), удержание
(retainability), мобильность (mobility) и транспортную часть integrity**; радио-параметры —
зона RAN. Влияние Core доказывается корреляцией своих счётчиков/трейсов с RAN-KPI.

Принципы изменения (пригодятся на защите):

1. **Baseline** — зафиксировать KPI до изменения (не менее 1–2 недель, с учётом профиля нагрузки).
2. **Один фактор** — менять одну группу параметров за раз.
3. **Guard-период** — после изменения наблюдать не менее 24–72 часов (или согласованный срок).
4. **Guard-KPI** — заранее определить, какие KPI не должны ухудшиться (иначе откат).
5. **Откат** — план возврата за ≤1 шаг, с сохранением конфигурации «до».
6. **Документирование** — что, когда, почему, результат, риски.

## 24.2 Метрики и KPI: что обязан знать Core-инженер

### 24.2.1 Радио-метрики (нужны для корреляции)

| Метрика | Смысл | Типовое использование |
|---|---|---|
| RSRP | уровень сигнала | покрытие, границы сот |
| RSRQ | качество сигнала | интерференция/нагрузка |
| SINR | отношение сигнал/шум | качество канала, MCS |
| CQI | индекс качества канала | адаптация модуляции |
| MCS | схема модуляции/кодирования | скорость |
| BLER | доля ошибочных блоков | надёжность радио |
| PRB utilization | загрузка ресурсных блоков | перегрузка соты |
| Timing Advance | удалённость UE | размер соты |

### 24.2.2 KPI ядра и радио (формулы, TS 32.450)

**Accessibility (доступность):**

- RRC Setup SR = успешные RRC Connection Setup / попытки RRC Connection Setup × 100%
- Initial Context Setup SR = успешные Initial Context Setup / попытки × 100%
- E-RAB Setup SR = успешно установленные E-RAB / запрошенные E-RAB × 100%
  (учитываются initial + additional bearer'ы; для 5G — PDU Session Resource Setup SR)
- Service Request SR = успешные Service Request / попытки × 100%
- Paging SR = ответившие на paging UE / paging-попытки × 100%

**Retainability (удержание):**

- E-RAB Drop Rate = аварийно сброшенные E-RAB / успешно установленные E-RAB × 100%
- Session drop rate (5G), RRC abnormal release rate

**Mobility (мобильность):**

- HO SR (intra/inter, X2/S1, N2/Xn) = успешные HO / попытки HO × 100%
- HO failure rate по типам: too early / too late / wrong cell (SON MRO-классификация)
- CSFB SR, EPS Fallback SR, SRVCC SR

**Integrity (целостность/производительность):**

- DL/UL throughput: объём PDCP SDU / время (на соту и на абонента)
- Latency: RTT или one-way delay (например, ping/замеры GTP-зондом)
- PRB utilization, число активных пользователей

**Важно для защиты:**

- KPI считаются по **попыткам**, а не по «плохим событиям»; знаменатель так же важен, как числитель.
- Счётчики Core (MME/SGW/PGW/AMF/SMF/UPF) и RAN (eNB/gNB) считаются **независимо**;
  их расхождение — сам по себе диагностический признак (потери на стыке/транспорте).
- Спецификации: TS 32.401 (концепции), TS 32.425 (E-UTRAN PM), TS 32.450 (E-UTRAN KPI),
  TS 28.552 (5G PM), TS 32.522 (SON), TS 32.422 (Trace), TS 37.320 (MDT).

**Пример расчёта (спросят на защите):** за час на соте 10 000 попыток E-RAB setup,
9 950 успешных → E-RAB Setup SR = 9 950 / 10 000 = 99,5%. Разбивка 50 отказов по cause:
40 — «transport resources unavailable», 10 — «radio resources not available». Вывод:
80% проблемы — транспорт/стык, а не радио. После изменения (ёмкость S1) повторный замер:
9 990 / 10 000 = 99,9%, guard-метрика (drop rate) не ухудшилась. Такой расчёт показывает
и результат, и зону ответственности.

### 24.2.3 Типовые целевые значения (ориентиры, зависят от сети)

| KPI | Ориентир |
|---|---|
| RRC Setup SR | ≥ 99% |
| E-RAB Setup SR | ≥ 99% |
| E-RAB Drop Rate | ≤ 0,5–1% |
| HO SR | ≥ 99% (intra), ≥ 98% (inter-RAT) |
| VoLTE MOS | ≥ 3,5–4,0 |
| RTP loss | ≤ 1% |
| Jitter | ≤ 30–50 мс |
| Paging SR | ≥ 95–98% |

## 24.3 QoS как главный рычаг Core

### 24.3.1 Параметры и точки применения

| Параметр | Где задаётся | Где применяется | Эффект в RAN |
|---|---|---|---|
| QCI/5QI | PCRF/PCF, HSS/UDM, PGW/UPF | eNB/gNB (scheduler) | приоритет, PDB, потери |
| ARP (1–15 + pre-emption) | PCRF/PCF, подписка | eNB/gNB (admission) | доступность при перегрузке |
| GBR/MBR | PCRF/PCF | eNB/gNB | гарантированная полоса |
| APN-AMBR | PGW (Gx) | PGW | ограничение non-GBR |
| UE-AMBR | MME/AMF (из подписки/PCRF) | **eNB/gNB** | суммарный лимит non-GBR |
| TFT/QoS rules | PGW/UPF, UE | UE + PGW/UPF | попадание трафика в bearer |

Точки передачи в RAN:

- 4G: S1AP **Initial Context Setup Request** и **E-RAB Setup Request** (E-RAB Level QoS Parameters:
  QCI, ARP, GBR/MBR);
- 5G: NGAP **PDU Session Resource Setup Request** (QoS flows: 5QI, QFI, ARP, GBR/MBR);
- изменения: S1AP E-RAB Modify, NGAP PDU Session Resource Modify;
- NAS: Activate/Modify Dedicated Bearer (TFT), PDU Session Modification (QoS rules).

### 24.3.2 Admission control и pre-emption

- eNB/gNB при установке GBR-bearer'а проверяет наличие ресурсов (**admission control**);
  при нехватке — отказ (E-RAB Setup Failure) или, при соответствующем ARP, **вытеснение**
  (pre-emption) менее важных bearer'ов.
- ARP: priority 1–15 (1 — высший), pre-emption capability (может ли вытеснять) и
  vulnerability (можно ли вытеснить).
- Core-ошибки: одинаковый ARP у голоса и данных; GBR без ARP-приоритета; «жадные» правила
  для второстепенного трафика — рост отказов и падение KPI доступности.

### 24.3.3 Практика

- VoLTE: QCI 1 (GBR) + ARP высокий, сигнализация QCI 5; 5QI 1 в 5G.
- VIP/корпоратив: отдельные правила, высокий ARP, GBR для критичных приложений.
- Игры/AR: QCI 3/5QI 3 или 79/80; низкий PDB.
- IoT: QCI 9/5QI 9, без GBR, минимизация сигнализации.
- Перегрузка: временное понижение AMBR, отключение необязательных GBR, backoff (см. 24.5).

## 24.4 Мобильность, зоны и steering

### 24.4.1 TA/зоны и paging

- **TA list (TAL)**: баланс между размером (меньше paging-нагрузки) и числом TAU (больше
  сигнализации). Оптимизация TAL — типовое Core-задание.
- **Paging**: MME/AMF отправляет S1AP/NGAP Paging в соты TA list; параметры: DRX-цикл
  (32/64/128/256 кадров; по умолчанию 64), число повторов, eDRX для IoT.
- Причины падения Paging SR: слишком большой TAL (много сот опрашивается), неверные TAL,
  несинхронные периодические TAU, перегрузка сигнализации, «спящие» IoT-устройства.
- Core-рычаги: пересмотр TAL, DRX/eDRX, таймеры (T3412/T3512), балансировка paging.
- **5G:** paging двух уровней — AMF пейджит UE в CM-IDLE через NGAP Paging; для UE в
  RRC_INACTIVE работает **RAN paging** в пределах **RNA** (RAN-based Notification Area),
  а вместо TAU — RNA update. Периодическая регистрация — T3512. Рычаги Core: T3512, eDRX,
  согласование с AMF; дизайн RNA — зона RAN, но влияет на сигнализацию ядра.

### 24.4.2 RFSP и приоритеты частот/RAT

- **RFSP (RAT/Frequency Selection Priority)** — индекс 1–256, который Core передаёт в RAN;
  eNB/gNB по нему выбирает RRM-политику: приоритет частот/RAT в idle (camping) и connected
  (HO preference).
- Источники: подписка (HSS/UDM — **SPID**), решение MME/AMF (override).
- Передаётся в S1AP/NGAP (Initial Context Setup, UE Context Modification, Handover Request и др.).
- Применение: удержание абонентов на ёмкостном слое (например, 2600 МГц), перевод на
  покрытийный слой на краю, steering 5G↔LTE, сегментация по типам абонентов/слайсам.
- Ошибки: RFSP, не согласованный с RRM-политикой RAN (эффект «не туда»), отсутствие политики
  для новых UE-категорий, конфликт с SON MLB.

### 24.4.3 Handover и пулы

- Типы: X2/Xn (прямой), S1/N2 (через Core); с переездом MME (S10) и/или SGW; inter-RAT (S3/S4, N26).
- Core-факторы успеха: доступность S10/N26, корректные пулы (MME/SGW/PGW), DNS-веса,
  отсутствие «дыр» в конфигурации соседей, ёмкость сигнализации.
- Пул-дизайн: S1-Flex (MME), SGW/PGW pools; перекос весов → перегрузка одного узла → падение
  HO/attach на части сот.
- Inter-RAT: CSFB (SGs), EPS fallback (N26), SRVCC (Sv) — параметры влияют на голосовые KPI.

## 24.5 Перегрузка и backoff

- **MME/AMF overload**: S1AP/NGAP Overload Start/Stop (например, «reject all», «permit emergency»,
  «permit high priority»); eNB снижает нагрузку по указанию Core.
- **NAS backoff**: T3346 (congestion), T3448 и др.; распределение таймеров предотвращает
  синхронные «волны» повторов.
- **Сигнальные штормы**: массовые attach/TAU (IoT, аварии, «умные» счётчики) — лечится
  eDRX/PSM, рандомизацией таймеров, распределением по пулам, rate-limit.
- **Приоритеты**: ARP pre-emption и MPS/экстренные вызовы сохраняют доступность для важного трафика.
- Метрики: RRC reject rate (причины: overload, admission), backoff-статистика, attach SR по часам.

## 24.6 Голос: VoLTE/VoNR, CSFB, SRVCC

Цепочка влияния Core на голос:

```
IMS (P-CSCF) → Rx → PCRF/PCF → Gx/N7 → PGW/UPF → S1AP/NGAP (QCI 1 / 5QI 1) → eNB/gNB
```

- Core-рычаги: GBR/ARP, TFT/flow-фильтры, DSCP-маркировка (EF), транспорт, кодеки (SDP:
  AMR-WB 12,65–23,85 кбит/с; EVS 5,9–24,4), jitter buffer, приоритет сигнализации (QCI 5).
- Метрики: MOS (цель ≥ 3,5–4,0), setup time (< 2 с), drop rate, RTP loss (< 1%), jitter (< 30–50 мс).
- **CSFB**: SGs, combined attach, TAC↔LAC mapping, redirection — типовые причины задержек
  (> 6–8 с) и отказов.
- **EPS Fallback (5G)**: N26, корректный IMS-voice флаг, скорость перевода в LTE — влияет на
  accessibility голоса в SA.
- **SRVCC**: Sv, подготовка PS→CS, потери при переводе — оптимизируется таймерами и конфигом.

## 24.7 Транспорт и размещение: вклад в latency и throughput

- **GTP-U**: накладные расходы 36 байт (внешний IP 20 + UDP 8 + GTP 8); MTU и фрагментация —
  типовой источник потерь и «загадочных» просадок.
- **DSCP**: голос — EF, сигнализация — AF/CS; проверка согласованности на всём пути.
- **Перегрузка S1/N3**: транспортные счётчики, drops, ретрансмиссии; отличать от перегрузки радио.
- **Размещение UPF/MEC**: ближе к абоненту — ниже latency; учитывать N6-локальность и политику.
- **CUPS**: U-plane масштабируется независимо; C-plane перегрузки лечатся пулами/overload.
- 5G: N3/N9, QoS-мэппинг в транспорт (DSCP), слайсинг транспорта.

## 24.8 Данные и инструменты оптимизации

### 24.8.1 Счётчики, трейсы, MDT, RCAF

- **PM-счётчики**: TS 32.425 (E-UTRAN), TS 32.450 (KPI), TS 28.552 (5G); выгрузка в OSS/BI.
- **Trace**: TS 32.422 (signaling-based, per-UE); трассировка по IMSI/GUTI на MME/AMF, eNB/gNB.
- **MDT**: TS 37.320 — измерения UE (RSRP/RSRQ, throughput) с геолокацией; logged/immediate.
- **RCAF**: TS 29.217 — функция осведомлённости о перегрузке RAN: сообщает PCRF (интерфейс Np),
  чтобы политики учитывали загрузку радио (данные из O&M).
- **Краудсорсинг/QoE-платформы** — массовые замеры с приложений, дополняют драйв-тесты.

### 24.8.2 SON и его связь с Core

- Функции SON: **ANR** (авто-соседи), **MRO** (устойчивость мобильности), **MLB** (балансировка),
  **CCO** (покрытие/ёмкость), **ES** (энергосбережение), RACH-оптимизация (TS 32.522, 36.300, 38.300).
- Core-смежные задачи: оптимизация paging/TA, согласование RFSP-политик с MLB, координация
  изменений (SON coordination), «заморозка» SON на время изменений Core.
- C-SON (OSS) vs D-SON (RAN); Core-инженеру важно: изменения Core не должны конфликтовать с SON.

### 24.8.3 Процесс оптимизации (PDCA)

1. **Plan**: цель (какой KPI, целевое значение), baseline, гипотеза, guard-KPI, план отката.
2. **Do**: изменение одного фактора в согласованном окне.
3. **Check**: сравнение KPI (до/после, по часам/сотам), проверка guard, разбор аномалий.
4. **Act**: закрепление/откат/доработка; документирование результата и побочных эффектов.

Инструменты по шагам: счётчики → drill-down по сотам/узлам → трейсы → MDT/краудсорсинг →
изменение → контроль 24–72 ч.

## 24.9 Кейсы (разбор для защиты)

**Кейс 1. E-RAB Setup SR упал на группе eNB.**
Данные: S1AP E-RAB Setup Failure с cause «radio resources not available» на одних сотах и
«transport resources unavailable» на других. Разбор: два разных корня — admission control
(ARP/GBR) и транспорт. Действие: пересмотреть QoS-профили (ARP), проверить S1-транспорт и
лицензии. Проверка: E-RAB SR + guard (drop rate, throughput).

**Кейс 2. HO SR упал после перераспределения пулов MME.**
Данные: рост S1-based HO failure, ошибки S10 на границе пулов. Причина: перекос DNS-весов и
«дыры» в конфигурации. Действие: выровнять веса, проверить S10 и соседей. Guard: RRC SR, attach SR.

**Кейс 3. Paging storm от IoT.**
Данные: синхронные periodic TAU каждые N минут, рост paging-нагрузки, падение Paging SR.
Причина: одинаковые таймеры + большой TAL. Действие: eDRX/PSM, рандомизация T3412, пересмотр TAL.
Guard: attach/TAU SR, загрузка сигнализации.

**Кейс 4. MOS VoLTE просел на части вызовов.**
Данные: RTP loss 2–3%, jitter 60 мс, QCI1 с GBR, но транспорт перегружен. Причина: перегрузка
S1-транспорта/DSCP-очередей. Действие: DSCP EF, ёмкость транспорта, проверка Rx/Gx-правил.
Guard: setup SR, drop rate.

**Кейс 5. Низкая скорость на краю соты.**
Данные: PRB utilization высокая, SINR низкий, AMBR не достигнут. Причина: радио-ограничение +
неоптимальный steering. Действие: RFSP-политики, перевод части абонентов на другой слой.
Guard: HO SR, RRC SR.

**Кейс 6. CSFB-вызовы дольше 8 секунд.**
Данные: SGs paging и redirection задержки. Причина: TAC↔LAC mapping, отсутствие redirect info.
Действие: исправить mapping, ускорить redirection. Guard: CSFB SR, возвраты в LTE.

**Кейс 7. Перегрузка MME в час пик.**
Данные: Overload Start, рост RRC reject, backoff T3346. Действие: распределение по пулам,
rate-limit для IoT, приоритеты. Guard: attach SR, emergency-доступность.

**Кейс 8. EPS Fallback не срабатывает в 5G.**
Данные: N26 не сконфигурирован, IMS-voice флаг не выставлен. Действие: включить N26, проверить
IMS-профиль. Guard: VoNR/EPS fallback SR, setup time.

**Кейс 9. Батарея IoT-устройств «садится».**
Данные: частые TAU/paging, нет eDRX/PSM. Действие: параметры энергосбережения, T3412/T3324.
Guard: доставляемость данных, задержка отклика.

**Кейс 10. DSS: просадка LTE после включения NR.**
Данные: PRB LTE ↓, скорость LTE ↓, NR получает ресурсы. Причина: дележ спектра (файл 18).
Действие: координация планировщиков, контроль KPI обоих слоёв. Guard: суммарная ёмкость.

## 24.10 Перекрёстные вопросы и ответы (для защиты)

**1. Как Core влияет на Accessibility, если радио — не его зона?**
Через QoS-профили и admission (ARP/GBR), управление перегрузкой (overload/backoff), paging и
зоны, пулы и DNS, голосовые процедуры (CSFB/EPS fallback). Core задаёт «правила доступа»,
RAN их исполняет.

**2. Почему UE-AMBR применяется в eNB, а APN-AMBR — в PGW?**
UE-AMBR — суммарный лимит non-GBR **по всем APN одного UE**; его видит только RAN (один радио-канал).
APN-AMBR — лимит **по конкретному APN**; точка агрегации — PGW/UPF. Оба могут ограничивать
скорость одновременно — смотреть оба.

**3. Что будет, если выдать QCI 1 без GBR?**
Класс голоса станет non-GBR-поведением: нет гарантии полосы и admission-приоритета — качество
деградирует при перегрузке. Проверять: GBR в S1AP E-RAB QoS и в правилах Gx.

**4. Как RFSP попадает в RAN и что при ошибке?**
Core (HSS/UDM + MME/AMF) формирует RFSP и передаёт в S1AP/NGAP (Initial Context Setup, HO и др.).
eNB/gNB сопоставляет RFSP с RRM-политикой. При рассогласовании абоненты «висят» не на том слое —
падение скорости или ёмкости.

**5. Почему большой TA list снижает Paging SR?**
Paging рассылается во все соты списка: больше сот — больше сигнальной нагрузки и коллизий,
дольше отклик. При этом маленький TAL → больше TAU. Нужен баланс; для IoT — eDRX.

**6. Как T3412 связан с сигнальными штормами?**
Одинаковый T3412 у массы устройств даёт синхронные periodic TAU. Лечится рандомизацией,
eDRX/PSM и распределением по времени; контролировать attach/TAU SR.

**7. Что такое MRO/MLB/CCO и где здесь Core?**
SON-функции RAN (устойчивость HO, балансировка, покрытие/ёмкость). Core влияет через пулы,
RFSP и зоны, а также обязан координировать свои изменения с SON (не «ломать» автонастройку).

**8. Какие счётчики докажут, что проблема на S1, а не в радио?**
Сравнить RAN-счётчики E-RAB Setup Failure по cause: «transport resources unavailable» (транспорт)
против «radio resources not available» (радио/admission). Плюс транспортные счётчики потерь на
S1-U и трассировки S1AP.

**9. Как отличить перегрузку транспорта от перегрузки радио?**
Транспорт: потери/задержки GTP-U, ретрансмиссии, дропы на S1/N3 при умеренном PRB.
Радио: высокая PRB utilization, рост BLER, низкий SINR/CQI. Оба могут сочетаться — смотреть
корреляцию по времени и сотам.

**10. Как проверить, что QoS-правило применилось в RAN?**
По S1AP/NGAP: E-RAB/QoS flow с ожидаемыми QCI/5QI, ARP, GBR; в RAN — счётчики scheduler'а и
распределение по классам; при сомнении — трейс на eNB/gNB и UE-side тест.

**11. Что делать при росте RRC reject?**
Классифицировать причину: MME overload (Overload Start), admission (ресурсы), backoff-таймеры,
транспорт. Затем: пулы/веса, rate-limit, приоритеты, ёмкость; guard — attach SR и доступность
экстренных.

**12. Как EPS fallback влияет на KPI 5G?**
Добавляет время установления вызова и переключение в LTE; ошибки N26/IMS-флага дают отказы
голоса. Метрики: EPS fallback SR, setup time, доля возвратов в NR.

**13. Как измерить MOS без драйв-теста?**
Анализ RTP на SGi/UPF (loss/jitter/кодек) + E-model; агрегация по сотам/абонентам; сравнение
с субъективными жалобами. Драйв-тест — точечная валидация.

**14. Что такое RCAF и зачем он нужен?**
Функция (TS 29.217), которая по данным O&M сообщает PCRF о перегрузке RAN (интерфейс Np),
чтобы политики (например, снижение битрейта видео) применялись только в перегруженных сотах.

**15. Какие guard-KPI при изменении ARP?**
E-RAB Setup SR (не должен упасть), drop rate, доступность экстренных/приоритетных, RRC reject.
Помнить: агрессивный pre-emption улучшает VIP, но ухудшает «массовые» сервисы.

**16. Почему HO SR падает после смены пулов MME/SGW?**
Перекос весов/DNS, отсутствие S10/N26-связности, «дыры» в соседях на границе пулов, разные
наборы функций. Проверка: S10/N26-статистика, распределение HO по парам узлов.

**17. Как slice-based steering в 5G влияет на RAN?**
Слайс определяет AMF/политики и может задавать RFSP/приоритеты; ошибки выбора NSSAI приводят
к неверному слою/узлу, росту отказов регистрации. Guard: registration SR, PDU session SR.

**18. Какие три числа показывают, что оптимизация удалась?**
(1) Целевой KPI — улучшился и стабилен; (2) guard-KPI — не ухудшились; (3) QoE-метрика
(MOS/жалобы/скорость) — подтверждает эффект. Плюс документированный откат.

**19. Чем paging в 5G отличается от 4G?**
В 5G два уровня: AMF пейджит UE в CM-IDLE через NGAP; для UE в RRC_INACTIVE работает
RAN paging внутри RNA, а вместо TAU — RNA update. Периодическая регистрация — T3512.
Это снижает сигнализацию ядра, но требует корректного дизайна RNA (зона RAN).

**20. Покажите пример расчёта KPI.**
10 000 попыток E-RAB setup, 9 950 успешных → 99,5%. Разбивка отказов по cause:
40 transport, 10 radio → приоритет действий — транспорт/стык. После изменения: 99,9%,
guard-метрики без ухудшения. Такой расчёт показывает и результат, и зону ответственности.

**Как отвечать на защите (структура):**
контекст → данные (счётчики/трейсы) → гипотеза → действие (1 фактор) → проверка (целевой + guard)
→ риск/откат → вывод. Никогда не «улучшайте» KPI без guard-метрик и окна наблюдения.

## 24.11 Чек-листы

### Симптом → где смотреть → действие

| Симптом | Core-точки проверки | Действие |
|---|---|---|
| RRC SR ↓ | MME overload, backoff, S1 SCTP | пулы/веса, rate-limit, ёмкость |
| E-RAB SR ↓ | admission (ARP/GBR), S1, лицензии | QoS-профили, транспорт, ёмкость |
| Drop rate ↑ | транспорт, HO, таймеры | корреляция с mobility, ёмкость |
| HO SR ↓ | S10/N26, пулы, TA, RFSP | выровнять веса, соседи, политики |
| Paging SR ↓ | TAL, DRX, T3412 | пересмотр TAL, eDRX, рандомизация |
| MOS ↓ | QCI1 GBR, DSCP, транспорт | Rx/Gx, очереди, ёмкость |
| Latency ↑ | UPF-размещение, N3/S1, MTU | переразмещение, MTU, маршруты |
| Reject ↑ | overload, admission, backoff | приоритеты, пулы, ёмкость |

### Параметры Core → эффект в RAN

| Параметр | Узел | Эффект |
|---|---|---|
| QCI/5QI, GBR/MBR | PCRF/PCF | приоритет, полоса, PDB |
| ARP | PCRF/PCF, подписка | admission, pre-emption |
| UE-AMBR | MME/AMF → eNB/gNB | лимит non-GBR на UE |
| TFT/flow-фильтры | PGW/UPF, UE | классификация трафика |
| RFSP/SPID | HSS/UDM, MME/AMF | выбор частот/RAT |
| TA list, T3412 | MME/AMF | paging/TAU-баланс |
| DRX/eDRX | MME/AMF | энергосбережение, paging |
| Overload/backoff | MME/AMF | управление перегрузкой |
| SGs/N26 | MME/AMF | CSFB, EPS fallback |
| DSCP, MTU | транспорт | потери, задержки, голос |
| Пулы/DNS-веса | MME/SGW/PGW | балансировка, устойчивость |

### Перед изменением (для протокола)

1. Цель и целевое значение KPI зафиксированы.
2. Baseline (≥1–2 недели) собран и сохранён.
3. Guard-KPI определены.
4. Окно изменения согласовано; SON «заморожен» при необходимости.
5. План отката готов (за 1 шаг).
6. После изменения: контроль 24–72 ч, отчёт, документирование.
